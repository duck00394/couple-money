# 期初餘額調整：設計分析

> **狀態：已於 Phase 3-4 C 依方案 A 實作完成**（沒有新增 schema 或 migration）。
> 實作細節見本文件末段與 `docs/11-Phase3-4-progress.md`。

## 問題

建立帳戶時輸入的期初餘額打錯了（例如把 $5,000 打成 $50,000），目前沒有任何地方可以改。
帳戶餘額的第一原則不變：**餘額一律由交易／調整記錄算出來（`餘額 = −Σ該帳戶的 payment`），
不可以直接改 `Account` 上的欄位作弊。**

## 目前程式碼已經有的東西

| 已存在 | 位置 | 狀態 |
|---|---|---|
| `TxType.ADJUSTMENT` | `prisma/schema.prisma` | 已在 enum 裡，**沒有任何地方寫入** |
| `buildBalanceLines("ADJUSTMENT", delta, account)` | `src/server/domain/ledger.ts:142` | 已實作、已有不變式檢查 |
| 不變式「只有 payment、沒有 split」 | `checkInvariants` | 已涵蓋 ADJUSTMENT |
| 不計入收支統計 | `INCOME_EXPENSE_TYPES` | 已排除 ADJUSTMENT |
| 不影響誰欠誰 | `DEBT_TYPES` | 已排除 ADJUSTMENT |
| 列表顯示 | `src/components/TxRow.tsx:60` | 已和期初餘額共用顯示（含正負號） |
| 搜尋類型 | `src/server/domain/search.ts` | **只有 `OPENING_BALANCE`，沒有 `ADJUSTMENT`** |

也就是說，A 方案的「地基」在 Phase 1 就已經鋪好了，只差一個服務函式與一個畫面。

## 三個方案

### A. 餘額調整交易（`TxType.ADJUSTMENT`）

新增一筆 `type = ADJUSTMENT` 的交易：一筆 payment（`amount = −delta`）、沒有 split。
原本打錯的期初餘額那一筆**完全不動**。

- **Audit trail**：最好。錯誤與更正兩筆都留著，看得到誰在什麼時候調整了多少、備註寫了什麼原因。符合「記帳 App 不竄改歷史」的慣例（和退款不改原始消費是同一個原則）。
- **對既有 Transaction 的影響**：零。不改任何既有資料列，不需要重算。
- **對 Debt 的影響**：零。`DEBT_TYPES` 不含 ADJUSTMENT，調整不會讓任何一方多欠或少欠。
  這是正確的產品語意——期初餘額打錯是「我對自己帳戶的認知錯誤」，不是「對方欠我錢」。
- **對 Fund designation 的影響**：需要注意，但規則已經存在。
  調整往下（delta < 0）會讓帳戶餘額變少，可能低於「已指定給基金」的金額。
  沿用目前的不變式：**調整後 `帳戶餘額 ≥ 已指定給基金`**，不成立就擋下來，
  訊息說明「這個帳戶有 $X 已經指定給基金，最多只能往下調 $Y」。
  這條檢查在 `assertEarmarkBacked` / `accountFreeAmount` 已經有，直接沿用即可。
- **對統計的影響**：零。`INCOME_EXPENSE_TYPES` 不含 ADJUSTMENT，月報表的收入／支出不會被污染。
  但**搜尋需要補一個 `ADJUSTMENT` 類型**（目前 `SEARCH_KINDS` 只有 `OPENING_BALANCE`），否則調整紀錄會查不到。
- **是否需要新的 transaction type**：不需要，`ADJUSTMENT` 已經在 enum 裡。
- **是否需要 approval**：建議**不需要**，但**個人帳戶要限制只有自己能調**（與 `updateAccount` 同一條規則：
  `account.ownerId === null || account.ownerId === me`）。共同帳戶兩人都能調，靠 audit log 互相看得到。
- **是否需要雙人帳本權限**：沿用現有 `assertCanWrite(ctx)`；唯讀成員不能調整。
- **Schema**：**不需要改**，也不需要 migration。

### B. 專門的 `AccountAdjustment` entity

另開一張表記錄調整，餘額計算改成 `−Σpayment + Σadjustment`。

- **Audit trail**：一樣好，但**餘額的真相被拆成兩個來源**。
- **對既有 Transaction 的影響**：大。每一個算餘額的地方（`getBalances`、`accountBalance`、
  `accountFreeAmount`、轉帳檢查、基金額度檢查、結算、統計）都要多查一張表並合併，
  漏掉任何一處就會出現「A 頁面顯示 $3,000、B 頁面顯示 $5,000」這種最難查的 bug。
  這正好違反「不要重寫既有財務核心」。
- **對 Debt 的影響**：一樣是零，但要另外寫測試證明它沒被算進欠款（A 方案是型別層面自動保證的）。
- **對 Fund designation 的影響**：同 A，但檢查點分散在兩套資料上。
- **對統計的影響**：預設就不在統計裡（因為不是 Transaction），
  但**列表、搜尋、詳細頁都看不到它**——使用者會覺得「我明明調整過，帳戶列表卻找不到那筆紀錄」。
  要解決就得在時間軸上把兩種資料合併排序，等於重寫列表與搜尋。
- **是否需要新的 transaction type**：不需要，但需要**新的 model + migration**。
- **是否需要 approval / 雙人權限**：與 A 相同。
- **Schema**：**需要新增 model 與 migration。**

### C. 其他做法

- **C1 直接編輯那一筆期初餘額交易**：實作最省，但**竄改歷史**——對方看不出金額被改過，
  而且目前期初餘額交易沒有走一般編輯流程（沒有 split、沒有樂觀鎖 UI）。
  若要做，至少要把舊值寫進 audit log。**不建議作為主方案。**
- **C2 作廢原期初餘額 + 重新建立一筆**：等於 C1 的「留痕版」，但時間軸上會出現一筆被刪除的期初餘額，
  比一筆「餘額調整 −$45,000」難懂。
- **C3 直接改 `Account` 的餘額欄位**：**違反第一原則，排除**（目前 `Account` 也根本沒有餘額欄位）。

## 建議

**採用 A。**理由：

1. schema 不用動、migration 不用加、財務核心不用重寫——風險最低。
2. 不竄改歷史，兩個人都看得到「誰、什麼時候、調了多少、為什麼」。
3. 欠款與統計的隔離是型別層面自動生效的（`DEBT_TYPES` / `INCOME_EXPENSE_TYPES` 已排除），
   不是靠每個呼叫點記得避開。
4. 基金額度的保護沿用現成的不變式，不需要新規則。

若真的實作，最小範圍會是：

| 要做的事 | 檔案 | 是否改 schema |
|---|---|---|
| `adjustAccountBalance(ctx, accountId, delta, note)`：鎖帳本 → 建 ADJUSTMENT 交易 → 檢查 earmark 不變式 → audit | `src/server/services/ledger.ts` | 否 |
| 個人帳戶只有自己能調 | 同上 | 否 |
| 防重送 `clientRequestId` | 同上 | 否 |
| 帳戶頁「調整餘額」表單（輸入**調整後的正確餘額**，系統自己算 delta，比較不會按錯） | `src/app/(app)/accounts` | 否 |
| 搜尋補 `ADJUSTMENT` 類型 | `src/server/domain/search.ts` | 否 |
| `updateAccount` 補 audit（目前改名／停用完全沒有留下稽核紀錄） | `src/server/services/ledger.ts` | 否 |

**需要你決定的兩件事（實作前）**：

1. 表單要讓使用者輸入「正確的餘額」（系統算差額）還是「要加減多少」？建議前者。
2. 共同帳戶的調整要不要需要另一半確認？建議不要（保持和記帳一致），只靠 audit log。

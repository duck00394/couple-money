# Couple Money — 需求分析與技術架構

> 版本：v0.1（Phase 1 開工前）｜產品暫名：**Couple Money**（名稱集中在 `src/config/app.ts`，日後改名只改一處）

核心資料鏈（整個 App 的骨幹）：

```
A. 記帳 → 分帳 → 應收應付 → 結算
B. 任務 → 打卡 → 獎金交易 → 共同基金 → 共同目標
```

兩條鏈最後都匯流到同一張 **Transaction（交易）總帳**。只要總帳正確，首頁、統計、匯出、備份都只是「讀取總帳」。

---

## 1. 哪些功能可以共用資料結構

| 共用結構 | 服務的功能 | 說明 |
|---|---|---|
| **Transaction（總帳）** | 消費、收入、退款、轉帳、結算、基金存提、基金支出、任務獎金、任務罰款、獎勵兌換、固定支出產生的帳單 | 用 `type` 區分，所有金錢變動只有這一個入口 |
| **TransactionPayment（誰付錢／誰收錢）** | 付款人、帳戶餘額、轉帳 Transfer Out/In、結算的付款與收款 | 每筆資金流動記錄「哪個人、哪個帳戶、流出多少」；帳戶餘額 = 加總 |
| **TransactionSplit（誰負擔）** | 分帳、多人分攤、專案分帳、共同支出統計 | 與 Payment 完全分開：Payment 是現金流，Split 是負擔 |
| **SplitRule（分帳規則）** | 帳本預設比例、分類預設比例、固定支出分帳 | 同一套規則引擎：EQUAL / RATIO / AMOUNT / FULL / SHARES |
| **Category + Tag** | 消費、收入、預算、固定支出、統計、搜尋 | 預算與統計直接以分類聚合 |
| **Recurrence（週期規則）** | 重複消費、固定支出、任務頻率、生日／紀念日提醒 | 同一種 RRULE-lite 結構（頻率、間隔、日、月），同一個「產生器」 |
| **Attachment** | 收據、基金圖片、目標圖片、打卡照片、專案照片、願望清單圖片 | 多型關聯（ownerType + ownerId） |
| **AuditLog** | 所有財務資料的新增／修改／刪除、權限變更、解除綁定 | 通知系統可從 AuditLog 衍生「對方修改了消費」 |
| **Project** | 約會、旅行、專案預算、專案統計 | Transaction.projectId；預算用 Budget(scope=PROJECT) |
| **Fund ↔ Goal** | 共同基金、共同目標、願望清單轉目標 | Goal.fundId 連結；目標進度 = 基金餘額（不另存數字） |
| **Book（帳本）作為權限邊界** | 所有資料 | 每張表都有 `bookId`，權限檢查只需檢查 BookMember |

## 2. 潛在衝突（以及採用的決策）

| # | 衝突 | 決策 |
|---|---|---|
| C1 | **存入共同基金／共同帳戶，算不算「對方欠我」？** 我存 1,000、對方存 0，若視為共有財產，數學上對方欠我 500 | **存入基金視為「投入」不是借款**：不影響誰欠誰，只統計「我的投入／另一半的投入」。從共同帳戶付的消費也不產生個人欠款 |
| C2 | **任務獎金的錢從哪來？** 如果只是「+50」但沒有真實現金，基金數字會跟銀行對不起來 | 獎金交易 `TASK_REWARD` 預設是「承諾入帳」：由指定的出資人帳戶（或「虛擬獎勵池」）轉入基金，兩種模式在 Phase 2 讓你們選；不論哪種都會有 Transaction |
| C3 | **帳戶餘額 vs.「不能直接改餘額」**：開帳戶時已經有錢 | 用 `OPENING_BALANCE` 交易建立初始餘額；對帳差額用 `ADJUSTMENT` 交易，永遠不直接改欄位 |
| C4 | **編輯歷史交易 vs. 已結算**：已經結清後改舊帳，欠款會重新出現 | 採「淨額制」（Splitwise 方式）：欠款永遠由總帳即時計算；改舊帳會正確反映新欠款，並寫入 AuditLog + 通知對方 |
| C5 | **退款**：退給誰？退款是收入嗎？ | 退款是獨立型別 `REFUND`，Payment 與 Split 皆為負值，會「沖銷」原消費的負擔；不算收入 |
| C6 | **轉帳**被統計成支出 | `TRANSFER` 型別在所有收支統計中排除；只影響帳戶餘額 |
| C7 | **多幣別** | Phase 1 每個帳本一個主幣別（TWD）；帳戶保留 currency 欄位，匯率換算延後 |
| C8 | **Viewer 權限 vs. 多人分攤** | Viewer 不能記帳，但可以被列為分攤對象（旅行朋友）；分攤對象用 BookMember，不一定要有登入帳號（Phase 3 支援「訪客成員」） |
| C9 | **解除綁定 vs. 保留歷史**：對方離開後仍需看得到誰付過錢 | 成員狀態改 `LEFT`，資料與姓名快照保留；不刪除 User 關聯 |
| C10 | **帳號刪除（個資）vs. 財務資料保留** | 刪除帳號 = 匿名化 User（姓名改「已刪除的使用者」、清 Email），交易保留 |
| C11 | **重複消費自動產生 vs. 重複產生** | 產生紀錄使用唯一鍵 `(recurringId, occurrenceDate)`，資料庫層擋重複 |
| C12 | **離線記帳（PWA）vs. 資料一致性** | 前端每次送出帶 `clientRequestId`（idempotency key），伺服器唯一鍵擋重送；真正的離線佇列放 Phase 5 |
| C13 | **Apple 登入、手機簡訊登入** 需要付費 | 見第 5 節，建議以 Passkey 取代 |

## 3. 應該延後的功能

| 功能 | 建議階段 | 理由 |
|---|---|---|
| Apple 登入 | 暫不做 | 需要 Apple Developer Program（US$99／年） |
| 手機簡訊登入 | 暫不做 | 簡訊發送需付費（Twilio 等每則約 NT$1–3）；Passkey 可提供同等便利 |
| 多幣別匯率 | Phase 5 之後 | 匯率 API 免費額度不穩；一般情侶記帳用不到 |
| 發票載具自動匯入 | 暫不做 | 財政部 API 需申請且有使用規範；先提供「發票號碼／載具備註」欄位 |
| 收據 OCR | 暫不做 | 免費方案準確度差、付費 AI API 違反原則 |
| 推播通知 | Phase 4 | Web Push 免費，但 iOS 需加入主畫面才能收；先做 App 內通知中心 |
| 離線寫入同步 | Phase 5 | 衝突處理複雜，先確保線上一致性 |
| 訪客成員（無帳號的分攤人） | Phase 3（專案） | 旅行才常用 |
| 批次操作 | Phase 3 | 依賴搜尋篩選 |

## 4. 技術架構

**單體 Web App + 關聯式資料庫 + 簡單 API**，不拆微服務。

| 層 | 選擇 | 為什麼 |
|---|---|---|
| Frontend | **Next.js（App Router）+ React + TypeScript + Tailwind CSS** + lucide 圖示 | 前後端同一個專案、同一種語言；Server Components 讓首頁資料一次讀好，手機開啟快；社群最大，AI 協作最熟悉；PWA 支援成熟 |
| Backend | **Next.js Server Actions + Route Handlers**，商業邏輯集中在 `src/server/*` 服務層 | 不需要另外架 API 伺服器；服務層是純 TypeScript，可單元測試，日後要換成 REST API 或 App 也能直接重用 |
| Database | **PostgreSQL** + **Prisma ORM** | 金錢必須靠資料庫交易（ACID）、唯一鍵、外鍵、行鎖（`SELECT … FOR UPDATE`）來防重複扣款與重複結算；Prisma 的 schema 可讀性高，migration 可追蹤 |
| Authentication | **自建 Email + 密碼（scrypt）+ 資料庫 Session（HttpOnly Cookie）**；Phase 5 加 **Google OAuth** 與 **Passkey（WebAuthn，Face ID／指紋）** | 不依賴付費服務；Session 存資料庫可以做「登出所有裝置」；生物辨識完全交給 WebAuthn，伺服器永遠拿不到指紋／臉部資料 |
| Storage | 開發：本機資料夾；上線：**Supabase Storage（免費 1GB）** 或 **Cloudflare R2（免費 10GB）** | 圖片上傳前在瀏覽器壓縮（≤300KB），免費額度可存數千張收據 |
| Deployment | **Vercel Hobby（免費，限非商業）+ Neon 或 Supabase Postgres（免費）**；或 **Docker Compose 自架**（家用電腦／NAS） | 私人使用完全在免費額度內；已附 docker-compose，不綁定任何平台 |
| 測試 | **Vitest**（分帳、結算、金額計算）+ 真實 Postgres 整合測試 + **Playwright** 手機截圖 | 財務邏輯必須有自動化測試 |

金額一律以 **整數「分」（minor unit）** 儲存，避免浮點誤差；分帳尾差用「最大餘數法」分配，確保加總永遠等於總額。

## 6. 資料庫結構（預估）

### Phase 1（本次實作）

```
User ─┬─ Session
      └─ BookMember ─── Book ─┬─ Couple（兩人關係、交往日、狀態）
                              ├─ Invite（邀請碼、到期、使用次數）
                              ├─ Account（owner=個人 或 null=共同）
                              ├─ Category（含子分類 parentId、預設分帳規則）
                              ├─ Tag
                              ├─ Transaction ─┬─ TransactionPayment（userId, accountId, amount 帶正負）
                              │               ├─ TransactionSplit（userId, amount 帶正負）
                              │               └─ TransactionTag
                              ├─ Settlement（from, to, amount → 對應一筆 SETTLEMENT 交易）
                              └─ AuditLog
```

**Transaction.type**：`EXPENSE` `INCOME` `REFUND` `TRANSFER` `SETTLEMENT` `OPENING_BALANCE` `ADJUSTMENT`
（Phase 2 新增 `FUND_DEPOSIT` `FUND_WITHDRAW` `FUND_EXPENSE` `FUND_TRANSFER` `TASK_REWARD` `TASK_PENALTY`；Phase 4 新增 `REWARD_REDEMPTION`）

**核心不變式（寫在服務層並有測試）**

1. 非轉帳類交易：`Σ Payment.amount = Σ Split.amount = 交易金額 × 方向`
2. 轉帳／結算：`Σ Payment.amount = 0`（一邊流出、一邊流入），沒有 Split
3. 帳戶餘額 = `−Σ Payment.amount`（該帳戶，未刪除交易）
4. 個人淨額 = `Σ(個人 Payment) − Σ(個人 Split)`；兩人淨額相加恆為 0；正數代表「別人欠我」
5. 從共同帳戶支付的交易，不產生個人欠款（決策 C1）
6. 所有財務寫入都在同一個 DB transaction 內，先鎖定 Book 列，再檢查、再寫入
7. `clientRequestId` 唯一鍵：同一個送出動作最多只會產生一筆交易
8. 刪除 = `deletedAt` 軟刪除；修改 = `version + 1` 並寫 AuditLog（before／after）

### Phase 2–4（預留，之後以 migration 加入）

```
Fund ── FundTransaction（對應 Transaction）      Goal（fundId 連結）
Task ── TaskSchedule ── CheckIn ── TaskReward／TaskPenalty（對應 Transaction）
     └─ TaskMilestone（unique: taskId + days → 每個里程碑只能領一次）
Budget ── BudgetCategory       RecurringExpense（unique: id + occurrenceDate）
Project ── ProjectMember       Reward ── RewardRedemption（對應 Transaction）
Achievement ── UserAchievement（unique: userId + achievementId）
CoupleEvent   Wishlist（→ 可轉 Goal）   Notification   Attachment
```

防重複的資料庫唯一鍵：

| 風險 | 唯一鍵 |
|---|---|
| 重複扣款／重送 | `Transaction(bookId, clientRequestId)` |
| 重複領獎 | `CheckIn(taskId, userId, date)`、`TaskReward(checkInId)` |
| 重複領連續獎勵 | `TaskMilestoneClaim(taskId, userId, milestoneDays, streakStartDate)` |
| 重複固定支出 | `RecurringOccurrence(recurringId, occurrenceDate)` |
| 重複結算 | `Settlement(bookId, clientRequestId)` + 鎖定後檢查未結清金額 |
| 重複基金入帳 | `FundTransaction(transactionId)` |

## 7. 頁面結構

```
/login  /register  /invite/[code]  /onboarding（建立帳本 或 輸入邀請碼）

App（手機：底部導覽；桌面：左側 Sidebar）
├─ 首頁 /                     今日支出｜誰欠誰｜今日任務*｜共同基金*｜目標進度*
├─ 記帳 /transactions         列表（依日期分組）、搜尋*
│   ├─ /transactions/new      支出／收入／退款／轉帳（大數字鍵盤）
│   └─ /transactions/[id]     詳細、編輯、複製、刪除
├─ 任務 /tasks*               今日打卡、待確認、連續天數
├─ 目標 /goals*               目標列表、進度
└─ 更多 /more
    ├─ 結算 /settle           誰欠誰、一鍵結算、部分結算、結算紀錄
    ├─ 帳戶 /accounts         餘額、帳戶間轉帳、新增帳戶
    ├─ 共同基金 /funds*       統計 /stats*   專案 /projects*
    ├─ 固定支出 /recurring*   預算 /budgets*
    ├─ 情侶 /couple*          紀念日、願望清單、獎勵商店
    └─ 設定 /settings         帳本（名稱、成員、權限、邀請、分帳預設、分類規則）、切換帳本、個人資料、登出
```
`*` = Phase 2 之後。Phase 1 會先放「即將推出」的入口，讓導覽結構一次定案。

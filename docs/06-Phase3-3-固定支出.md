# Phase 3-3 固定支出（Recurring Expenses）

## 核心概念

固定支出是**排程設定**，不是金流：

- 建立設定不會扣任何帳戶、不會產生 Transaction、不影響統計
- 到了應付日，使用者按「產生記帳」才會建立真正的一筆支出
- 產生出來的 Transaction 用 `recurringExpenseId` + `recurringDueDate` 記住來源

沒有背景排程，也不會在使用者沒有操作的情況下自動扣錢。

## Migration

`20260918013134_phase3_3_recurring_expenses`

- 新增 `RecurringExpense`（含 `RecurringFrequency`、`RecurringStatus` 兩個 enum）
- `Transaction` 新增 `recurringExpenseId`、`recurringDueDate`（DATE）
- **唯一鍵** `Transaction(recurringExpenseId, recurringDueDate)`：同一個固定支出的同一個應付日，資料庫層級只允許一筆

沒有新增分帳、帳戶、分類相關的資料表，全部重用既有結構（`splitRule` 與記帳同一種 JSON 格式）。

## 週期

只支援三種：

| 週期 | 設定 | 說明 |
|---|---|---|
| 每週 | 星期日～星期六 | |
| 每月 | 1～31 日 | 該月沒有這天 → 當月最後一天（2 月 31 → 2/28、閏年 2/29） |
| 每年 | 月份 + 日期 | 同樣套用「當月最後一天」規則 |

所有日期運算都用專案既有的 `YYYY-MM-DD` + UTC 基準工具，台灣時間 9/18 不會變成 9/17。

## 下一次應付日（nextDueDate）

- 建立時：從 `max(開始日期, 今天)` 起算第一個週期 → **不會補歷史**
- 產生後：從「這次的應付日 + 1 天」起算 → 逾期時可以逐期補產生（一次一期）
- 重新啟用：從今天起算；如果今天這期已經產生過，直接跳到下一期
- 超過結束日期 → `nextDueDate = null`（已結束）
- 只改金額／名稱／分類不會動到 `nextDueDate`；改週期或起訖日期才會重新計算

## 產生實際交易

走既有的記帳流程（`createTransactionIn`），所以分帳、金流、欠款、稽核、基金連動全部是同一套邏輯：

- `occurredAt` = 應付日（不是按下按鈕的當天）
- 金額、分類、名稱、備註、分帳規則都取自固定支出當下的設定
- 付款帳戶照原本規則：個人帳戶會產生欠款，共同帳戶不產生欠款，信用卡則是未繳金額增加（繳卡費仍走 Phase 3-2 的轉帳）

### 防重複產生（三層）

1. 畫面送出時帶著顯示中的應付日，與目前的 `nextDueDate` 不同 → `RECURRING_STALE`
2. 交易的 `clientRequestId` 固定為 `recurring:<id>:<應付日>`
3. 資料庫唯一鍵 `(recurringExpenseId, recurringDueDate)`

再加上 `lockBook` 的帳本鎖，兩支手機同時按也只會有一筆。

### 其他限制

- 還沒到應付日不能產生（`RECURRING_NOT_DUE`）
- 停用中不能產生（`RECURRING_PAUSED`）
- 付款帳戶已停用 → 擋下來並顯示「此固定支出使用的帳戶已停用，請先修改付款帳戶。」，不會自動換帳戶

## 修改、停用、刪除

- **修改**：只影響之後產生的交易，已經產生的歷史交易完全不動
- **停用**：不再出現在待處理、不能產生；歷史交易與設定都保留
- **重新啟用**：不補停用期間漏掉的付款
- **刪除**：soft delete，只刪設定；已經產生的交易全部保留（刪除前會提示還有幾筆）

## 與其他階段的關係

- **退款（Phase 3-2）**：固定支出產生的交易可以照常退款；退款不會修改固定支出，也不會改 `nextDueDate`
- **搜尋（Phase 3-1）**：新增類型「固定支出產生」，關鍵字也會搜固定支出名稱；列表列與詳細頁都看得到「📅 固定支出：房租」，可以點回設定頁
- **基金／任務**：固定支出不碰基金指定金額與任務獎金

## 畫面

- 記帳頁 →「📅 固定支出」（有待處理時顯示數字）
- 首頁在有待處理時多一行「有 N 筆固定支出待處理」，其他區塊沒有改動
- `/recurring`：待處理（今天／逾期）、即將到期、已停用／已結束
- `/recurring/[id]`：設定摘要、已產生的記帳清單、停用／刪除、收合式的修改表單

## 權限

同一個帳本的兩個人都可以新增、修改、停用、重新啟用、刪除、產生交易；所有 server action 都以 `bookId` 過濾，別的帳本查不到、改不了、也產生不了（直接開網址是 404）。

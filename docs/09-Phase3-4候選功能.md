## 候選功能

### A. 統計與報表 `/stats`

1. **功能名稱**：統計與報表（月報、分類佔比、兩人負擔比、趨勢）
2. **解決的問題**：現在只看得到「本月總支出」一個數字。使用者問「這個月錢花去哪了」「我們是不是外食變多了」「我跟他誰負擔比較多」都答不出來。
3. **影響的資料模型**：只讀 `Transaction` / `TransactionPayment` / `TransactionSplit` / `Category`。不寫入任何表。
4. **需要 schema**：否
5. **需要 migration**：否
6. **影響既有財務邏輯**：否，但**必須重用既有規則**：`INCOME_EXPENSE_TYPES` 決定什麼算收支（轉帳／結算／期初／調整都不算）、退款從支出扣除、基金投入不是交易。不可以另寫一套加總。
7. **需要新權限**：否（唯讀成員本來就看得到）
8. **需要並發控制**：否（純讀取）
9. **複雜度**：中低（無寫入、無 migration，主要成本在查詢聚合與手機圖表）
10. **與核心流程的關聯**：直接長在 Transaction 總帳上，是「總帳正確 → 統計只是讀取」的兌現。

### B. 預算（分類月預算與超支提醒）

1. **功能名稱**：預算 Budget
2. **解決的問題**：只看得到花了多少，看不到「還能花多少」。情侶最常見的爭執點是「這個月外食超標了嗎」。
3. **影響的資料模型**：新增 `Budget`（scope：帳本／分類／專案）＋ `BudgetCategory`；讀取 Transaction 聚合。
4. **需要 schema**：**是**
5. **需要 migration**：**是**
6. **影響既有財務邏輯**：否。預算是讀取後的比較，不產生任何 Transaction、不影響餘額與欠款。但「什麼算進預算」必須沿用 §A 同一套規則。
7. **需要新權限**：建議沿用 `assertCanWrite`（唯讀成員只能看）。是否要「只有建立者能改預算」需要你決定。
8. **需要並發控制**：低（兩人同時編輯同一個預算 → 用既有的 `updatedAt` 樂觀鎖即可）
9. **複雜度**：中（依賴 A 的聚合；月份邊界與時區要沿用帳本時區）
10. **與核心流程的關聯**：與 Fund 概念上容易混淆——**Fund 是「已經存在、被指定用途的錢」，Budget 是「打算花多少的上限」**。文件與畫面必須講清楚，否則會破壞現有心智模型。

### C. 餘額調整（`TxType.ADJUSTMENT`）

1. **功能名稱**：帳戶餘額調整（對帳差額）
2. **解決的問題**：期初餘額打錯了沒有地方改；長期使用後 App 餘額與實際銀行餘額對不起來。
3. **影響的資料模型**：只新增 `Transaction(type=ADJUSTMENT)` + 一筆 `TransactionPayment`。不動既有資料列。
4. **需要 schema**：**否**（enum、`buildBalanceLines`、不變式、列表顯示都已存在）
5. **需要 migration**：**否**
6. **影響既有財務邏輯**：**否，但必須遵守兩條既有不變式**：不進 `DEBT_TYPES`（不產生欠款）、不進 `INCOME_EXPENSE_TYPES`（不算收支）；往下調整必須通過「帳戶餘額 ≥ 已指定給基金」。
7. **需要新權限**：個人帳戶只有擁有者能調（與 `updateAccount` 同一條規則）；共同帳戶兩人都能調。
8. **需要並發控制**：**是**——`lockBook` + `clientRequestId` 防重送（與記帳相同）。
9. **複雜度**：低（設計已完成，見 `docs/08`）
10. **與核心流程的關聯**：直接維護「Account = 真實資金所在地」這條原則；沒有它，帳面會慢慢失真。

### D. 分類管理（新增／改名／停用／排序／預設分帳規則）

1. **功能名稱**：分類管理
2. **解決的問題**：分類是建立帳本時種下去的固定 14 個，使用者不能新增「寵物」「房貸」，也不能停用用不到的。`Category.splitRule`（例如房租固定 40/60）完全沒被使用。
3. **影響的資料模型**：`Category`（已有 `parentId` `splitRule` `sortOrder` `isArchived`）；`Transaction.categoryId` 只讀不動。
4. **需要 schema**：**否**
5. **需要 migration**：**否**
6. **影響既有財務邏輯**：**間接會**。停用分類時**不可以**改動既有交易的 `categoryId`（會竄改歷史）；刪除分類必須是 archive 而不是真刪，否則舊交易會變成孤兒。分類預設分帳規則只在「新建記帳時帶入預設值」，**不可以回頭重算既有交易的 Split**。
7. **需要新權限**：`assertCanWrite`；是否需要另一半同意才能停用分類，需要你決定。
8. **需要並發控制**：低～中（`updatedAt` 樂觀鎖；排序批次更新要在同一個 DB transaction 內）
9. **複雜度**：中低
10. **與核心流程的關聯**：影響記帳、固定支出、搜尋、統計、預算五個地方的下拉選單，是 A／B 的前置條件之一。

### E. 記帳收據照片

1. **功能名稱**：交易附件（收據）
2. **解決的問題**：現在只有打卡能上傳照片。消費收據、發票、帳單都無處可放，事後對帳只能靠記憶。
3. **影響的資料模型**：`Attachment`（`ownerType` 是自由字串，新增 `"TRANSACTION"` 即可）；Transaction 不變。
4. **需要 schema**：**否**
5. **需要 migration**：**否**
6. **影響既有財務邏輯**：否（附件不參與任何金額計算）。但**刪除交易時附件要跟著 soft delete**，否則會留下 Phase 3-4 前驗收抓到的那類殘留資料。
7. **需要新權限**：沿用 `readAttachment` 既有的帳本檢查；唯讀成員可看不可傳。
8. **需要並發控制**：低（上傳與綁定要在同一個 DB transaction，避免「圖片上傳成功但交易建立失敗」的孤兒檔案）
9. **複雜度**：低（瀏覽器壓縮、上傳、API 路由都已存在，等於接線）
10. **與核心流程的關聯**：不碰財務核心，純粹是記帳流程的補強。

### F. 批次操作（依賴 Phase 3-1 搜尋）

1. **功能名稱**：搜尋結果批次改分類／加標籤／刪除
2. **解決的問題**：補記一整個月的帳之後，要一筆一筆改分類非常痛苦。架構文件把它排在 Phase 3 且註明「依賴搜尋篩選」——搜尋已在 3-1 完成。
3. **影響的資料模型**：`Transaction`、`TransactionTag`；批次刪除會連帶 Payment／Split／FundTransaction／退款關聯。
4. **需要 schema**：否
5. **需要 migration**：否
6. **影響既有財務邏輯**：**會，而且風險最高的一個**。批次刪除必須逐筆走既有的 `deleteTransaction`（保留基金額度不變式檢查、退款關聯檢查、固定支出關聯），**不可以為了效能寫一段 `deleteMany`**。批次改分類不影響金額，相對安全。
7. **需要新權限**：`assertCanWrite`；批次刪除是否要另一半同意（沿用既有 `DeleteRequest` 機制）需要你決定。
8. **需要並發控制**：**是**——整批在同一個 `lockBook` + DB transaction 內，任何一筆失敗全部回滾；且要有筆數上限。
9. **複雜度**：中高（風險來自「一次動很多筆」，不是來自技術）
10. **與核心流程的關聯**：直接寫入總帳，是所有候選裡**最容易破壞既有不變式**的一個。

### G. 匯出與備份（CSV／JSON）

1. **功能名稱**：資料匯出
2. **解決的問題**：資料鎖在一個 App 裡，換工具、報稅、做自己的試算表都拿不出來；也沒有任何備份手段。
3. **影響的資料模型**：全部唯讀。
4. **需要 schema**：否
5. **需要 migration**：否
6. **影響既有財務邏輯**：否（純讀取）
7. **需要新權限**：**需要你決定**——唯讀成員可不可以把整本帳匯出？
8. **需要並發控制**：否
9. **複雜度**：低～中（欄位定義與跨表攤平要想清楚，技術上不難）
10. **與核心流程的關聯**：是「總帳是唯一真相」的驗證工具，也能拿來跟 `scripts/data-integrity-check.ts` 互相對照。

### H. 通知中心（App 內，不做推播）

1. **功能名稱**：通知中心
2. **解決的問題**：另一半改了、刪了、結算了、產生了固定支出，你完全不會知道。架構文件 C4 明確寫「改舊帳會寫入 AuditLog + 通知對方」，但通知那半段沒做。
3. **影響的資料模型**：新增 `Notification`（或先做成 AuditLog 的唯讀視圖 + 已讀時間戳）。
4. **需要 schema**：**看做法**——純讀 AuditLog 的「動態牆」不需要；要有已讀狀態就需要。
5. **需要 migration**：同上
6. **影響既有財務邏輯**：否（AuditLog 已經在每個服務函式內寫好）
7. **需要新權限**：否（同帳本本來就互相看得到）
8. **需要並發控制**：低
9. **複雜度**：低（唯讀動態牆）～中（含已讀狀態）
10. **與核心流程的關聯**：不碰金額，但顯著降低「對方偷偷改帳」的不安感——這是雙人帳本的核心情緒問題。

### I. 專案（約會／旅行）＋ 訪客成員

1. **功能名稱**：Project 與訪客分攤對象
2. **解決的問題**：一趟旅行的花費散在明細裡，算不出「這趟總共花多少、誰欠誰」；跟朋友一起出遊時，朋友沒有帳號也要能被列為分攤對象（架構文件 C8）。
3. **影響的資料模型**：新增 `Project` / `ProjectMember`；`Transaction` 新增 `projectId`；**`BookMember` 要允許沒有 `userId` 的訪客**。
4. **需要 schema**：**是（而且改動最大）**
5. **需要 migration**：**是**
6. **影響既有財務邏輯**：**會，而且是全部四條鏈**。「兩人帳本」目前是很多地方的隱含假設（`ctx.partner`、欠款只有兩人、`net` 兩人相加為 0）。加入第三個分攤對象會影響分帳引擎、欠款計算、結算、首頁、搜尋的「付款人」選項。
7. **需要新權限**：**是**——訪客成員不能登入、不能寫入，只能被列為分攤對象。
8. **需要並發控制**：與既有相同，但要新增「專案刪除 vs. 專案內還有交易」的檢查。
9. **複雜度**：**高**（這次候選裡最高）
10. **與核心流程的關聯**：會動到「Debt 根據交易計算」這條最核心的假設。建議**不要**放在 3-4。

### J. 願望清單／獎勵商店

1. **功能名稱**：Wishlist → Goal、Reward → RewardRedemption
2. **解決的問題**：想買的東西沒地方記，也無法一鍵變成共同目標；任務累積的獎金除了進基金之外沒有「兌換」的成就感。
3. **影響的資料模型**：新增 `Wishlist`、`Reward`、`RewardRedemption`；兌換要對應一筆 Transaction（架構文件預留 `REWARD_REDEMPTION`）。
4. **需要 schema**：**是**
5. **需要 migration**：**是**
6. **影響既有財務邏輯**：**會**——兌換是真的從基金扣錢，必須沿用「未入金獎金不是現金」「基金支出要明確指定付款 Account」兩條規則，等於再實作一次 Fund Expense 的完整檢查。
7. **需要新權限**：需要你決定（兌換要不要另一半同意）
8. **需要並發控制**：**是**（同一筆獎勵被兩人同時兌換）
9. **複雜度**：中高
10. **與核心流程的關聯**：架構文件把它放在 Phase 4，建議維持。

### K. 帳本與成員管理（解除綁定、帳號匿名化、多帳本）

1. **功能名稱**：成員狀態與帳號生命週期
2. **解決的問題**：分手、換帳本、刪帳號目前完全沒有出口；`MemberStatus.LEFT`、`BookStatus`、C9／C10 的決策都寫好了但沒實作。
3. **影響的資料模型**：`BookMember`、`Book`、`User`（匿名化）；歷史交易一律保留。
4. **需要 schema**：**否**（欄位都在）
5. **需要 migration**：否
6. **影響既有財務邏輯**：**會**——`ctx.partner` 目前假設一定存在且是 ACTIVE。成員離開後欠款怎麼呈現、能不能繼續結算、姓名快照怎麼顯示，都是**產品規則問題不是技術問題**。
7. **需要新權限**：**是**（誰可以踢人、誰可以解散帳本）
8. **需要並發控制**：中（解除綁定與記帳同時發生）
9. **複雜度**：中（技術中等，產品決策很重）
10. **與核心流程的關聯**：碰到權限邊界（Book）本身，影響每一頁。

## 依風險排序的建議

| 風險 | 候選 |
|---|---|
| 不碰財務核心、不需要 schema | **A 統計**、**C 餘額調整**、**E 收據照片**、**G 匯出**、**H 通知中心**、**D 分類管理** |
| 需要 schema 但不改既有金流規則 | **B 預算** |
| 會動到既有寫入路徑，需要很小心 | **F 批次操作** |
| 會動到「兩人帳本」的根本假設 | **I 專案／訪客成員**、**K 成員生命週期** |
| 等於再做一次基金支出 | **J 願望清單／獎勵商店** |
